Lumari

Enabling Secure Structural Self-Evolution in Multi-Agent Systems
via Retrieval-Augmented Blueprint Generation

Patrick Zilke

Masterarbeit — Zwischenstand

22. Mai 2026

Motivation

Multi-Agenten-Systeme (MAS) haben feste Team-Strukturen — neue Aufgabentypen erfordern manuelle Anpassungen.

Status Quo

  • Statische Agenten-Topologie
  • Nur vordefinierte Tools nutzbar
  • Unbekannte Aufgabe → Fail
  • Bestehende Systeme (z.B. AgentOrchestra) generieren nur neue Tools, keine neuen Rollen

Lumari

  • Structural Self-Evolution — System erkennt Lücken und baut autonom neue Skills
  • Erfolgreiche Blueprints werden in Vektordatenbank gespeichert
  • Wiederverwendung bei ähnlichen Aufgaben
  • Semantischer Gatekeeper blockt unsicheren Code

Use Case: Baustellenberichte aus Audio-Transkripten generieren — variable Anforderungen, ideal als Testbed für Self-Evolution.

Forschungsfragen

RQ1 — Effektivität: Führt strukturelle Selbst-Evolution zu einer höheren Task-Completion-Rate als statische MAS-Architekturen?
Metrik: Pass@1 (Cold vs. Warm)
RQ2 — Effizienz: Reduziert die Wiederverwendung autonom generierter Blueprints den Ressourcenverbrauch bei nachfolgenden Aufgaben gleichen Typs?
Metrik: Token-Verbrauch, Latenz, Build-Skip-Rate
RQ3 — Sicherheit: Kann ein semantischer Gatekeeper gefährliche Code-Beschreibung-Diskrepanzen in autogenerierten Agenten-Tools zuverlässig erkennen?
Metrik: Accuracy, FPR, FNR

Gatekeeper (Sicherheit)

Autogenerierter Code ist ein Sicherheitsrisiko — der Gatekeeper prüft vor Aktivierung, ob der Code zur Beschreibung passt.

✓ Safe: csv_parser

Beschreibung: "Parst CSV-Dateien"

Code: import csv, Standardbibliothek

→ PASS — Code macht was beschrieben

✗ Unsafe: area_calculator

Beschreibung: "Berechnet Flächen"

Code: import os; os.system(...)

→ BLOCK — Lying Tool erkannt

Prüfmechanismus (zweistufig):

  1. AST-Analyse: Statische Prüfung auf blockierte Imports/Konstrukte (os, subprocess, eval, exec, socket, open, ...)
  2. Semantische Validierung: Embedding-Vergleich von Code-Verhalten vs. Beschreibung (Schwellenwert 0.7)

Erkenntnis: Wo liegt die Grenze von Blueprint-Reuse?

  • Build-Phase eliminiert — aber nur ~10% der Gesamttokens (Skill-Pipeline ~10–20k/Skill)
  • Execution dominiert — Berichtsgenerierung kostet ~40–50k Tokens/Task, unabhängig ob Skill neu oder reused
  • Prompt-Overhead wächst — statische Skill-Zuordnung, nicht-zugewiesene Skills bei allen Agents (kein Task-basiertes Filtering)
  • Confounder — DNS-Instabilität verursacht LLM-Retries, verzerrt Warm-Run-Messung
Fazit RQ2: Blueprint-Reuse eliminiert die Build-Phase komplett (stärkster Einzeleffekt), aber Gesamttokens sinken nicht. Für echte Effizienzgewinne bräuchte es:
  • Gelernte Execution-Pläne — bekannte Task-Typen mit weniger Waves/LLM-Calls ausführen
  • Template-Reuse — Berichtsstruktur wiederverwenden, nur Fakten einsetzen
  • Task-basiertes Skill-Filtering — per Embedding-Match nur relevante Skills laden statt alle verfügbaren

Status: Was klappt & was nicht

✓ Funktioniert

  • Self-Evolution Loop — System baut Skills und verbessert sich über Zeit
  • L1/L2: 96% Pass@1 — einfache und kombinierte Berichte zuverlässig
  • 5-Rollen Skill-Pipeline mit Sandbox-Testing und Retry
  • Gatekeeper: 100% Accuracy auf Testkorpus
  • Blueprint-Reuse eliminiert Build-Phase komplett
  • Faktenrecall — Zahlen, Namen, Normen wörtlich übernommen

✗ Offene Probleme

  • L3/L4: 62–67% — analytische Berichte zu komplex
  • L5 (DB+Audio): 0% — Skills werden gebaut aber nicht als Tools aufgerufen
  • Statistik — Wilcoxon nicht signifikant (p=0.22, braucht mehr Seeds)
  • Seed-Varianz hoch (63–97%) durch DNS-Outages als Confounder
  • Domain Transfer — 4% Pass@1 (Strukturabschnitte fehlen)
  • FeasibilityJudge-Bugs — mehrfach gefixt, fragile Komponente

Kann ich so abgeben?

Ja, mit Einschränkungen. RQ1 + RQ2 beantwortbar (Self-Evolution funktioniert, Blueprint-Reuse spart Build-Phase). RQ3 mit 100% Accuracy belegt. Hauptschwächen: statistische Signifikanz (mehr Seeds nötig) und L5-Tasks. Empfehlung: Einen sauberen Final-Run + L5-Fix priorisieren, dann schreiben.
